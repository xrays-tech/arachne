    Tutorial

    从嵌入到多节点：渐进式上手

    这一节从“为什么这样设计”讲起：先建立一致性直觉（ReadIndex、get_stale、CP），再走一遍 server::Arachne 的完整生命周期，最后拆开参考节点，看 RaftNode + WalStorage + Runtime + Handle 是怎么真实装配起来的。

    1. 它由什么组成

    Arachne 首先是一个库。共识、WAL 和 KV 状态机构成 arachne-kv 核心； 核心只面向 seam 特征（Transport、Storage、 StateMachine、Clock、Rng、 FsyncObserver……）编程，核心内没有任何具体时钟、RNG、网络代码或文件 I/O。 具象的传输由嵌入方插进来——生产环境用 arachne-kv-transport-tonic，测试用内存传输。

    嵌入方

    你的进程

    创建节点、持有 Handle、发起读写与成员操作；嵌入方只与库的公开 API 交互。

    核心

    arachne-kv

    raft 共识 + WAL + KV 状态机。传输无关，--no-default-features 时零外部 crate。

    传输

    arachne-kv-transport-tonic

    tonic / HTTP-2 / rustls。由 transport-tonic 特性启用的具象传输。

    参考节点

    arachne-node

    把存储 + 传输 + HTTP 接好的二进制：既能跑真实集群，也可当作嵌入库的装配范例。

    2. 一致性语义：先说清楚再写代码

    操作集保持小而明确；下表与 arachne/src/client/mod.rs / README 完全一致：

    Operation语义实现
    put / delete 线性化写 追加到 raft 日志，仲裁持久化后提交，应用于状态机后应答。
    get 线性化读（默认） ReadIndex：leader 上经仲裁确认的读，在 applied ≥ read_index 后服务；非 leader 返回 NotLeader 并被重定向。
    get_stale 允许任意陈旧 直接读本地状态机；跨调用不保证单调。
    失去仲裁 写/线性读 → 失败 CheckQuorum + leader 主动退位：get/put 返回 QuorumUnavailable，get_stale 继续可用。

    ReadIndex 线性读

    线性化读不依赖 leader lease 或时钟漂移边界。请求被路由到当前 leader （非 leader 返回 NotLeader 并带 leader 提示），leader 先以一轮仲裁心跳 确认自己仍居主导地位，等读索引应用到状态机后再返回值。整个操作被一个有界 deadline 约束（超时为 Timeout）。

    get_stale 的“陈旧”是怎么回事

    get_stale 直接读本节点的已应用状态机：任何节点都能答（无需重定向）， 可以陈旧，而且文档明确写为不保证单调——连续两次调用可能看到乱序的值。 它的价值在于失去仲裁时仍可读——这是 CP 系统在一致性与可用性之间的取舍。

    CP 语义：失去仲裁时宁可失败

    Arachne 是 CP 系统：任何时刻至多一个 leader；写与线性读都需要仲裁； 失去仲裁时每个线性化操作都失败（QuorumUnavailable），而不是退化为 读多写少或分裂脑。错误是显式、带类型的（详见第 8 节与 API Reference）。

    3. 嵌入：facade 生命周期

    arachne_kv::server 提供一个“零 tokio、单实例”的 facade：进程内一个节点， 挂在全局静态槽上。完整程序在 Quick Start，这里拆开生命周期讲每一步的为什么。

    ① start —— 引导节点（single_node = N=1 集群）

    rust
    // One node per process. 同步调用：绑定即装配完成。
Arachne::start(ClusterConfig::single_node(1, &dir, WalConfig::default()))?;

    data_dir 按需创建；WAL 的数据目录锁被获取并持有到节点生命周期结束。 节点运行在自己的独立线程（current-thread tokio runtime）上，调用方从不轮询 runtime。 以 {self} 作为唯一投票集（raft 的 is_singleton 路径）， 所以节点第一个 tick 就自选为 leader，线性读免去仲裁轮。

    ② 等选主 —— 一个有界轮询

    rust
    // Pre-election reads fail fast (fast non-leader redirect). Poll until Ok.
let deadline = Instant::now() + Duration::from_secs(5);
loop {
    match Arachne::get(b"hello").await {
        Ok(v) => break,                       // 成为 leader，读到 None（键未设置）
        Err(ArachneError::NotLeader { .. })
        | Err(ArachneError::QuorumUnavailable) => {
            if Instant::now() >= deadline { panic!("node never became ready within 5s"); }
            tokio::time::sleep(Duration::from_millis(10)).await;
        }
        Err(e) => panic!("unexpected read error: {e}"),
    }
}

    为什么需要这一步？get 需要 leader。start 是同步的，但选主是 异步发生的；等第一个线性读成功，节点才算真正就绪。Quick Start 的示例 facade.rs 也是这样处理的。

    ③ 读写 —— set / get / get_stale / delete

    rust
    Arachne::set(b"hello", b"world").await?;          // 线性化写
let value = Arachne::get(b"hello").await?;          // ReadIndex 线性化读
let stale = Arachne::get_stale(b"hello").await?;    // 本地（弱）读
Arachne::delete(b"hello").await?;                   // 线性化删除
assert_eq!(Arachne::get(b"hello").await, Ok(None));

    ④ shutdown —— 显式收尾

    rust
    // Frees the static slot and releases the WAL lock. 再次调用返回 NotInitialized。
Arachne::shutdown()?;

    节点不会随 Arachne 标记对象丢弃而关闭——该标记只是 装饰性的；必须显式 shutdown() 来释放数据目录锁并 join 线程。

    如果想把 facade 暴露在 HTTP 端点（而非直接调用静态方法），可用一个 Web 框架 包裹它：仓库自带 examples/axum_http.rs，把 set/get/get_stale/delete 映射到 PUT/GET/GET?stale=1/DELETE， 嵌入方只需 #[tokio::main] + curl（详见 Quick Start §3）。

    4. Handle：完整的客户端表面

    facade 的五个静态方法背后其实都是一个 Handle。需要更多能力时，用 Arachne::handle() 拿一个克隆（共享 actor 通道，clone 只是引用计数加一）：

    rust
    let handle: Handle = Arachne::handle().await?;
handle.put(b"k", b"v").await?;
let (voters, learners) = handle.membership().await?;

    重定向 / 重试策略

    一次操作若返回 NotLeader 且带提示，Handle 会针对提示的进程内 对端（或在确定顺序中的下一个已知对端）重试：最多跟随 Handle::MAX_REDIRECTS（3）次重定向，整个尝试限定在一个选举超时的总 deadline 内，超时返回 Timeout；不知道 leader / 失去仲裁返回 QuorumUnavailable。客户端与节点共享进程，重定向是客户端侧的（节点保持无状态）。

    i

    Handle::without_redirect() 得到一个单发克隆，跳过整个重定向策略， 原样返回 NotLeader{hint}。参考节点的 HTTP 面用的正是它——多进程部署里 follower 应回答 409 + leader 提示，而不是塌缩成 QuorumUnavailable。

    5. 多节点：参考节点怎么装配

    多节点集群也可以直接走 facade：Arachne::start(ClusterConfig::member(..)) 每进程一个节点即可组集群（见 Quick Start）。本节展示底层 Runtime / Handle 装配——需要完全程序化控制时用这一层； 参考节点 arachne-node 的 node.rs 是现成的装配示例，核心接线如下 （省略调优参数）：WAL → tonic 传输 → Runtime actor → 线程。

    rust
    // 1) 打开 WAL（数据目录锁取在节点生命周期）
let wal = WalStorage::open(
    &config.data_dir,
    WalOptions {
        cluster_id: config.cluster_id.clone(),
        node_id: config.node_id.as_str().to_string(),
        config: WalConfig {
            fsync_policy: profile.fsync_policy,
            segment_bytes: profile.wal_segment_bytes,
        },
        created_at_millis: now_millis(),
        fsync_observer: None,
    },
)?;

// 2) tonic 传输：factory 拥有集群身份与地址表，只绑定本进程自己的 listener
let factory = TonicTransportFactory::new(
    config.cluster_id.clone(), 1, 0, Vec::new(), config.addresses.clone(),
);
factory.start_with_bind(config.node_id.clone(), config.listen).await?;
let (tx, rx) = factory.create(config.node_id.clone());

// 3) 运行时配置：其他成员的 raft id = initial_cluster 中的 1 基下标
let runtime_config = RuntimeConfig {
    self_raft_id: config.raft_id,
    self_node_id: config.node_id.clone(),
    peers,
    addresses: config.addresses.clone(),
    raft: RaftNodeConfig::from_profile(profile),
    profile: profile.clone(),
    metrics: Arc::clone(&metrics),
};

// 4) 装配 actor 并拿到客户端 Handle；actor 做阻塞式 fsync，独占一条 OS 线程
let (runtime, handle) = Runtime::new(runtime_config, wal, tx, rx, &logger)?;
let _thread = runtime.spawn_dedicated()?;

    HTTP 面则用一个单发 handle 挂在 Hyper HTTP/1.1 服务后面：

    rust
    let handler = Arc::new(NodeHttp {
    metrics: Arc::clone(&metrics),
    kv: node.handle().without_redirect(),   // follower 回答 409 + leader 提示
});
// tokio::net::TcpListener::bind(config.http_listen).await?;
// http::serve(listener, handler, shutdown).await?;

    优雅关闭的顺序有讲究：先停 HTTP，再关 tonic factory（关闭入站流，结束 actor 的 recv），最后 join actor 线程（drop WAL、释放数据目录锁）。 另有一个 force-recovery 子命令实现手工单节点恢复 （arachne-node force-recovery --help）。

    6. 成员管理

    成员操作要走 leader（成员变更附加到日志、经仲裁持久化），所以客户端 API 与 HTTP / CLI 一一对应。一次成功的成员变更只在已应用（持久化）后应答，而不只是已提出—— 所以 200 之后立刻读 /members 就能看到新配置。

    操作Handle 方法HTTP
    加 learner（不投票，只追日志） add_learner(node_id) POST /members/add-learner/<id>
    把追平的 learner 提升为投票成员 promote_learner(node_id) POST /members/promote/<id>
    移除成员（leader 会先移交领导权） remove_member(node_id) POST /members/remove/<id>
    移交领导权给指定成员 transfer_leader(node_id) POST /members/transfer-leader/<id>
    读当前成员（(voters, learners)） membership() GET /members → voters=1,2,3 learners=4

    几条纪律值得记住：

    • 单发事务：同一时刻至多一个成员变更在进行，第二个会被 ConfChangePending 拒绝；普通写不受影响。
    • 先追平再提升：learner 落后超过阈值（或从未应答 leader）时提升会被 LearnerNotCaughtUp{behind, threshold} 拒绝——把日志不完整的节点放进仲裁会破坏安全。
    • 移除 leader 是两步：自动先把领导权移交给其他投票者，再由新 leader 提出移除；无仲裁 / 无人可移交时移除失败且什么都没提出。

    CLI 子命令与这些操作一一对应（子命令在二进制名之后）：

    console
    $ arachne-node add-learner --config node2.toml --id 4
$ arachne-node promote --config node2.toml --id 4       # 等 4 追平再提升
$ arachne-node members --config node2.toml              # 读回已应用成员
$ arachne-node remove --config node2.toml --id 4
$ arachne-node transfer-leader --config node3.toml --id 1
# --http <ip:port> 可覆盖配置里的 http_listen（该端口为 0 时用）

    变更类子命令 --id 必填（读操作 members 不需要）；完整形态如下（子命令在二进制名之后）：

    console
    arachne-node add-learner|promote|remove|transfer-leader|members --config <path.toml> [--id <raft-id>] [--http <ip:port>]

    这些运维命令不跟随 leader 提示——409 body 里会告诉你该指哪个节点。 transfer-leader 须在领导权真正移交后才应答。

    7. 底层单节点：RaftNode + WalStorage + KvStateMachine

    想知道“核心”长什么样？single_node.rs 展示了最小完整嵌入：打开真实 WalStorage，在无对端的内联传输上装配 RaftNode，自己驱动 Ready 循环直到选主并提交一条 Put。没有测试脚手架、没有异步 runtime。

    rust
    use arachne_kv::consensus::RaftNode;
use arachne_kv::state_machine::KvStateMachine;
use arachne_kv::storage::{FsyncPolicy, WalConfig, WalOptions, WalStorage};
use arachne_kv::{StateMachine, Transport, TransportRx};

type Node = RaftNode<WalStorage, NullTx, NullRx>;

fn wal_opts() -> WalOptions {
    WalOptions {
        cluster_id: "example".into(),
        node_id: "n1".into(),
        config: WalConfig {
            fsync_policy: FsyncPolicy::Always,
            segment_bytes: 1 << 20,
        },
        created_at_millis: 1_700_000_000_000,
        fsync_observer: None,
    }
}

let wal = WalStorage::open(&dir, wal_opts()).expect("WAL must open");
let mut node = RaftNode::new(
    1,
    HashMap::new(),        // single node: the bootstrap voter set is {self}
    wal,
    NullTx,
    NullRx,
    0,                     // applied: 0 for a fresh node
    &Logger::root(slog::Discard.fuse(), o!()),
)
.expect("node must assemble");
let mut sm = KvStateMachine::new();

// One Ready cycle: tick, step, apply committed entries, advance apply.
fn drive(node: &mut Node, sm: &mut KvStateMachine) {
    node.tick();
    let entries = block_on(node.step())
        .expect("Ready cycle must succeed")
        .committed;
    for (index, _kind, data) in entries {
        sm.apply(index, &data).expect("applying a committed entry must succeed");
    }
    node.advance_apply();
}

// 自选为 leader（单节点：前几个周期内就能选上）
for _ in 0..500 {
    drive(&mut node, &mut sm);
    if node.leader_id() == 1 { break; }
}

// 提议一条 Put（状态机编码），驱动到提交并应用
let cmd = KvStateMachine::encode_put(1, 1, b"key", b"value");
node.propose(&cmd).expect("propose must succeed on the leader");
for _ in 0..500 {
    drive(&mut node, &mut sm);
    if sm.get(b"key").expect("read must succeed") == Some(b"value".to_vec()) { break; }
}

    注意这里的传输是两个自定义 half：NullTx（每个 send 立即失败， 因为没有对端）与 NullRx（recv 永不返回）。真实部署时它们换成 tonic 的 TonicTransport / TonicRx。嵌入方也可以只驱动 Runtime actor（第 5 节）而完全不用自己管 Ready 循环。

    8. 错误类型

    所有操作都是 Result<_, ArachneError>，错误显式且带类型。最常用的：

    • NotLeader { leader_hint } —— 非 leader；提示（可能过期）给出 leader 及其地址，客户端应重定向。
    • QuorumUnavailable —— 失去仲裁：leader 已退位、无已知 leader，或 ReadIndex 仲裁轮失败。
    • Timeout —— 有界等待耗尽，结果未知：写可能落也可能没落。
    • Busy —— 背压：提议队列或读等待队列满，重试即可，非致命。
    • SessionTableFull / SessionExpired —— 写会话表机制。
    • ShuttingDown / Unrecoverable —— 节点关停 / 致命存储错误（进程应 fail-stop）。
